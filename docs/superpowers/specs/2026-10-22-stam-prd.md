---

## 1. Summary

Stam is a free, modern, browser-based family tree builder. Unlike form-based genealogy tools
where people float around randomly, Stam is **systematic**: one generation per row, the head
of the family at the top, children below, spouses beside their partner, siblings side by side.
Users build the tree directly on the canvas with one-click "+" handles and smart drag & drop; the
layout arranges itself. Trees export to PNG, JPEG, SVG, PDF (poster or tiled), self-contained
interactive HTML, JSON and GEDCOM.

All data stays in the user's browser. There are no accounts, no server storage and no tracking
of family data.

The product ships with an award-quality landing page whose hero *is* the product: the real layout
engine builds a family row by row as the visitor scrolls.

## 2. Problem

- **Form-based tools are slow.** Most free builders make you fill a form per person and then
  link records by ID. Building a 50-person tree takes hours.
- **Free-canvas tools get messy.** Diagram tools (draw.io, Canva) let you place boxes anywhere,
  so trees become tangled, uneven and hard to extend. Every new child means re-arranging by hand.
- **Real families are not simple.** Remarriage, divorce, adoption, half-siblings and
  step-relations break most simple tree tools.
- **Exports are poor.** Many tools only export low-resolution images or require a paid plan for
  printable PDF posters.
- **Privacy concerns.** Large genealogy platforms require accounts and keep family data
  (including living people) on their servers.

## 3. Users

| Persona | Need | Typical tree |
|---|---|---|
| **Family historian** | Record the whole extended family accurately, import/export GEDCOM | 100–2,000 people, 4–8 generations |
| **Occasion maker** | Make a beautiful printable tree for a wedding, reunion, gift or school project | 15–60 people, 3–4 generations |
| **Curious relative** | Quickly sketch "who is who" and answer "how are we related?" | 20–100 people |
| **Multilingual family** | Names in Urdu/Arabic script alongside Latin, RTL interface | any size |

## 4. Goals and non-goals

### Goals (v1)
1. A new user builds a 3-generation, 15-person tree in **under 5 minutes** without reading help.
2. The layout is always tidy: **no overlapping cards, no crossing child lines**, generations aligned.
3. Export quality good enough to print an A1 poster with sharp text.
4. Correctly model real families: multiple marriages, divorce, adoption, step and half relations.
5. Works fully offline after first load; data never leaves the device unless the user exports it.
6. Landing page reaches award-site quality (Awwwards rubric ≥ 8 in every category on internal QA).

### Non-goals (v1)
- User accounts, cloud sync, real-time collaboration, share links (planned for later, see §16).
- DNA matching, record search, historical document hosting.
- Non-Gregorian calendars (Hijri, etc.) for date entry.
- Native mobile apps (the web app is responsive and touch-capable instead).
- Free-form manual placement of cards (rejected in favour of auto layout).

## 9. Data model

Union-centric, mirroring GEDCOM's INDI/FAM structure.

```ts
type Gender = 'male' | 'female';

type FuzzyDate = {
  qualifier?: 'about' | 'before' | 'after' | 'between';
  year?: number; month?: number; day?: number;
  toYear?: number;                       // for 'between'
};

interface Person {
  id: string;                            // nanoid
  firstName: string;
  lastName: string;
  nickname?: string;
  nativeName?: string;                   // e.g. Urdu/Arabic script
  gender: Gender;
  isPlaceholder?: boolean;               // "Unknown father/mother"
  isLiving: boolean;
  birth?: { date?: FuzzyDate; place?: string };
  death?: { date?: FuzzyDate; place?: string };
  photoId?: string;                      // blob key in IndexedDB
  notes?: string;
}

type UnionStatus = 'married' | 'partner' | 'engaged' | 'divorced' | 'separated' | 'widowed';
type ChildType = 'biological' | 'adopted' | 'step' | 'foster';

interface Union {
  id: string;
  partners: [string] | [string, string]; // person ids
  status: UnionStatus;
  start?: FuzzyDate;
  end?: FuzzyDate;
  children: { personId: string; type: ChildType }[]; // array order = sibling order
}

interface TreeDocument {
  id: string;
  name: string;
  schemaVersion: number;
  rootPersonId?: string;
  persons: Record<string, Person>;
  unions: Record<string, Union>;
  unionOrder: Record<string, string[]>;  // personId -> ordered union ids
  settings: { theme: string; colorMode: string; direction: 'ltr' | 'rtl' };
  createdAt: string;
  updatedAt: string;
}
```

**Invariants** (enforced by `core/model` validation, tested):
- Every id referenced in a union exists in `persons`.
- A person is a `biological` child of at most one union (they may additionally be an
  adopted/foster/step child of other unions).
- No person is their own ancestor.
- A union has at least one partner.

## 10. Architecture

A pure-TypeScript core (no DOM) with a thin React layer.

```
src/
  core/
    model/       types, validation, invariants, schema migrations
    commands/    addPerson, addChild, addSpouse, addParent, addSibling, relink,
                 reorder, updatePerson, deletePerson, ... (each returns a new doc; undo via immer patches)
    layout/      family, pedigree, hourglass, descendants, fan, timeline layouts
                 → { nodes: PositionedCard[], edges: Connector[], bounds }
    kinship/     relationship calculator + per-language term tables
    dates/       FuzzyDate parse/format/compare
  io/
    json/        import/export + migrations
    gedcom/      tokenizer, parser, mapper, writer
  export/
    render/      layout result → standalone SVG string (shared by all exports)
    svg/ png/ jpeg/ pdf/ html/
  storage/       IndexedDB (idb): trees, photos, snapshots; BroadcastChannel for multi-tab
  i18n/          react-i18next setup, locale files, RTL handling
  ui/
    app/         editor shell, toolbar, tree list
    canvas/      SVG viewport, pan/zoom, culling, minimap, drag & drop
    cards/       person card, handles, inline editor
    panels/      person panel, calculator, birthdays, export dialog
  site/          landing page (sections, motion engine)
  routes/        React Router routes (client)
  server.ts      Bun dev server (Bun.serve + HTML imports + HMR)
scripts/
  build.ts       bun build → dist/ (hashed assets, code splitting)
  prerender.ts   static HTML for / and 404
```

| Unit | Purpose | Interface | Depends on |
|---|---|---|---|
| `core/model` | Types + validation | `validate(doc): Issue[]` | — |
| `core/commands` | All mutations | `apply(doc, cmd): { doc, patches, inverse }` | model |
| `core/layout` | Positioning | `layout(doc, view, opts): LayoutResult` (pure) | model, dates |
| `core/kinship` | Relationship | `relate(doc, a, b, lang): Relationship[]` | model |
| `io/gedcom` | GEDCOM | `parse(text): { doc, report }`, `write(doc): string` | model |
| `export/render` | SVG string | `renderSvg(layout, theme, opts): string` | layout |
| `storage` | Persistence | `TreeRepo` (list/get/save/delete/snapshots) | model |
| `ui/*` | React UI | components + Zustand store | everything |

**State:** one Zustand store holds the active `TreeDocument`, selection, view, viewport and
collapsed set. Edits go through `core/commands` only; immer patches feed the undo stack.

**Rendering:** the canvas renders `LayoutResult` as SVG. The same `LayoutResult` feeds
`export/render`, guaranteeing exports match the screen.

### 10.1 Layout engine (family view)

1. **Generation assignment:** BFS from the root through parent/child links; partners share
   their partner's generation. Generation = row; `y = generation × rowHeight`.
2. **Couple blocks:** a blood relative and their partners form one block. One partner:
   `[Person]═[Spouse]`. Several: `[Spouse 1]═[Person]═[Spouse 2]═…`, ordered by `unionOrder`.
   Each union's children hang from the midpoint of that union's connector.
3. **Subtree measurement:** bottom-up width calculation, contour-based packing (Reingold–Tilford
   style) so neighbouring branches nest without overlap; parents centred over their children.
4. **Connectors:** orthogonal routes: union connector → vertical drop → sibling bar → child.
   Styles: married = solid double; partner/engaged = solid single; divorced/separated = dashed;
   adopted/foster/step child line = dotted.
5. **Pedigree collapse:** a person reached twice is placed at the first position; others become
   linked-copy nodes.
6. **Collapsed branches:** excluded from layout; parent card gets a `+N` badge.
7. **Animation:** UI interpolates node positions between layouts (250 ms cards, 400–600 ms full
   re-flow, expo-out); disabled under reduced motion.

Other views reuse steps 3–4 with different traversals (pedigree = ancestor binary tree;
hourglass = pedigree mirrored above descendants; fan = polar transform of pedigree; timeline =
x by year).

## 11. UX overview

- **Start screen (`/app`):** tree list + "New tree" + "Import (JSON/GEDCOM)" + backup reminder.
- **Editor:** top toolbar (tree name, undo/redo, view switcher, search, calculator, export,
  settings), canvas centre, generation ruler on the left margin (I, II, III…), side panel on the
  right (bottom sheet on mobile), minimap bottom-right, zoom controls bottom-left.
- **Card:** photo circle (or initials), name (+ native name on a second line when present),
  years `1950 – 2019` with tabular figures, gender marker on the card edge, deceased treatment.
  Width 180 px, height 72 px at 100%.
- **Empty state:** one card "Start with a person" centred on the ruler at generation I.
- **Onboarding:** 3-step dismissible coach marks on first open (add child, drag to reorder,
  export). No modal tutorial.

## 14. Testing strategy

| Layer | What | Tool |
|---|---|---|
| Core model/commands | Every command + its inverse; invariants after every command | bun test |
| Layout | Property tests on 10,000 random families: no card overlaps, children below parents, parents centred within tolerance, rows aligned, deterministic output. Snapshot tests for ~20 named fixtures (remarriage, adoption, cousin marriage, 5,000-person stress) | bun test + fast-check |
| Kinship | Table-driven tests: ≥ 60 relationship cases incl. half, step, in-law, removed cousins, pedigree collapse | bun test |
| GEDCOM | Round-trip on a corpus (own fixtures + public sample files); malformed-input fuzzing | bun test + fast-check |
| Dates | Parse/format/compare of fuzzy dates | bun test |
| UI components | Card, handles, panels, store wiring | bun test + happy-dom |
| Exports | SVG snapshot (bun test); PNG/PDF smoke tests in a real browser (file valid, dimensions) | bun test / Playwright |
| UI flows | Create tree, quick-add, drag reorder, relink, undo, export, import, RTL switch | Playwright |
| Accessibility | axe on app and landing; keyboard-only E2E flow | Playwright + axe-core |
| Landing | `/awwwards` QA loop: screenshots, vitals, critic score ≥ 8 | shoot.mjs / audit.mjs |
| Performance | Layout benchmarks (1k / 5k people) in CI with budgets | mitata via `bun run bench` |

## 15. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Layout engine complexity (remarriage + pedigree collapse + collapsing) | High | Build first in M1 with property tests; linked-copy rule keeps the graph a tree |
| Browser storage cleared by user/browser | High (data loss) | Persistent storage request, rolling snapshots, backup reminders, easy JSON export |
| Huge PNG exports exceed canvas limits (esp. iOS Safari) | Medium | Cap size per browser, warn, suggest PDF/SVG |
| Font embedding for Arabic/Urdu in SVG/PDF exports (shaping) | Medium | Spike in M2; fall back to converting text to paths for PDF |
| GEDCOM dialect variance between vendors | Medium | Lenient parser + import report; test with files from major vendors |
| Bun dev server / bundler gaps vs Vite (e.g. plugin ecosystem, font/asset handling, worker bundling) | Medium | Spike the build + prerender script and worker bundling first in M1; keep `scripts/build.ts` small and explicit |
| Scope size of v1 | Medium | Milestones are independently shippable; P1/P2 items can slip |
